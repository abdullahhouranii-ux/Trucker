# Trucker — Stage 2, Part 2: shipment publication, quotation, booking and resource reservation (provisional)

Version 0.3, 13 Nov 2026. Owner: Abdullah. Builds on the Stage 1 baseline and Stage 2 Part 1 (v0.3). Authoritative copy: `docs/specs` in the repository; Claude-project copies are synchronised references. Changes in 0.3: substitution cannot waive hard requirements (7.2); an occupied resource blocks dispatch of its next booking (7.3); foundation-only setup waits for no decision (12). Changes in 0.2 after review: the flow is stated as agent-shaped and provisional until D-001; substitution has commercial rules; conflict flags are concurrency-safe; retry rules have security boundaries; reservation expectations follow lifecycle state; TBD items are split into approved rules and operating parameters. No application tests were run; this is a document.

**Status.** Provisional design; nothing is implemented. D-001 (commercial model), D-002 (payment approach) and D-003 (launch geography) remain **TBD**. **The booking flow drafted here is agent-shaped**: a carrier or owner authors a quotation and the shipper accepts it, giving one agreement between those two parties. Under a principal model the contracting parties differ and there are two linked agreements with Trucker in the middle; that is a structural difference that no visibility setting resolves. Sections 5 to 8 are therefore **provisional until D-001** and booking implementation waits for it. Section 9 separates what holds under either model from what does not. No payment model is designed. No supplier is selected and no legal, tax or licensing compliance is asserted. Policies marked **TBD** are listed in section 10.

## 2. Separate state models

| Object | States | Notes |
|---|---|---|
| **Shipment** (the request) | `draft` → `published` → `awarded`; or `withdrawn`, `expired`; later `closed` | Commercial life only. Movement belongs to the trip (Part 3) |
| **Quotation** | `submitted` ↔ `countered` → `accepted`; or `rejected`, `withdrawn`, `expired`, `not_selected` | A separate advisory **availability flag** (7.1) is not a state. Every change of price or terms creates a new numbered version; only the latest version can be accepted |
| **Booking** | `confirmed` → `cancelled` or `completed` | Created only by acceptance. A possible `pending_payment` step depends on D-002 and is not designed |
| **Reservation** (one per truck, trailer, driver) | `active` → `released` or `consumed` | Time-based; the only source of truth for availability |

## 3. Rules that apply to every journey

### 3.1 Time and time zones

| Rule | Detail |
|---|---|
| Storage | Every moment is stored as an absolute instant in UTC |
| Location time | Each location carries its own time zone. Pick-up and delivery windows are entered and shown in the **location's** local time, with the zone named |
| Viewer in another zone | Sees location time first, own time second |
| Deadlines | Quotation validity, shipment expiry and reassignment deadlines are absolute instants, judged by the server clock only; device clocks are never trusted |
| Windows | Half-open intervals: a window ending at 14:00 does not overlap one starting at 14:00 |
| Date-only values | Not used for anything that drives a rule |
| D-003 effect | With one country there is one zone in practice; cross-border lanes can have pick-up and delivery in different zones, which this design already handles |

### 3.2 Idempotent retries

| Rule | Detail |
|---|---|
| Key | Every command that creates or changes something carries a unique request key generated by the client: portal, mobile or partner system |
| Scope of a key | A key is unique only within **organisation + caller (user or API client) + operation**. The same key value from another organisation, caller or operation is a different request and can never return someone else's result |
| Order of checks | 1 authenticate, 2 authorise against **current** permissions, 3 only then look up the key. A caller whose access was removed since the first attempt is refused and does not receive the stored result |
| Same key, same content | Returns the stored outcome; nothing happens twice. The stored outcome holds only what that caller was entitled to see |
| Same key, different content | Refused with a clear error; the request content is compared by fingerprint |
| Two identical requests at once | The first registers the key as in progress under a uniqueness constraint. The second does not execute; it receives "in progress, retry shortly" |
| Atomic storage | The key record, the business change and its outcome are saved in the same database transaction. If the change is rolled back the key record is rolled back too, so a retry runs afresh |
| What is stored | Completed outcomes, including definite business refusals (for example "already awarded"), so the same key always gives the same answer |
| Retryable failures | Network timeout, server error, "in progress", rate limit: retry with the **same** key. Validation errors, permission refusals and business refusals are final for that key; a corrected request needs a new key |
| Retention | Keys are kept longer than the longest permitted client retry window. After expiry a reused key is treated as a new request, so clients must stop retrying before then. The period is a technical parameter set at Stage 3. Driver trip events use permanent event identifiers instead (Part 3) |
| Stale screens | Shipment and quotation carry a version number; a command sent against an old version is refused and the client reloads |

### 3.3 Partial-failure recovery

| Failure | Handling |
|---|---|
| Any step of acceptance fails | Acceptance, booking, reservations and closing of other quotations happen in **one database transaction**. Either all of it is saved or none |
| Client loses the connection after the server saved | The client retries with the same key and receives the existing booking |
| Notification or partner webhook cannot be sent | The message is written in the same transaction as the booking (outbox) and delivered afterwards with retries; exhausted deliveries appear in an operations queue. Nothing is announced for a booking that was not saved |
| Attached file upload fails | Files are uploaded first, then attached; unattached files are cleaned up |
| Hidden inconsistency | A scheduled check compares each booking with the reservations expected for its lifecycle state (7.3). The expected number of findings is zero; any finding alerts operations |

## 5. Journey J3: discovery and quotation

| Aspect | Specification |
|---|---|
| Actors and permissions | Carrier `admin` or `dispatcher`; owner or a delegate holding `offer_and_book`; partner client with `quotations:write`. The organisation must be verified and eligible for the shipment (capability, equipment, geography, documents valid through the delivery window) |
| Fields | Shipment and its version; amount and currency; what the amount includes (**TBD**, section 9); validity until (required); nominated truck; nominated trailer where the shipment needs one; nominated driver (optional at this point: **TBD** P-201); earliest pick-up the carrier can meet; notes |
| States | `submitted`; `withdrawn` by its author; `expired` at validity end; `rejected` by the shipper |
| Validation | One open quotation per organisation per shipment; nominated assets must be under the quoting party's operating control (Part 1, 3.5) and compatible with the shipment; validity not later than the quotation deadline; amount positive, in the shipment's currency, with that currency's precision |
| No hold at quotation time | A quotation does **not** reserve anything. The same truck may be quoted on several shipments; the first acceptance wins and the others receive an advisory availability flag (7.1) |
| Failure paths | Eligibility lost after quoting (quotation suspended, author told); nominated asset becomes unverified (author asked to substitute); shipment edited (re-confirmation, J2) |
| Notifications | New quotation to the shipper; withdrawal; nearing expiry to the author; expired |
| Audit events | `quotation.submitted`, `quotation.withdrawn`, `quotation.expired`, `quotation.rejected` |
| Acceptance | AT-211 an ineligible or unverified organisation cannot see or quote the shipment. AT-212 a quotation is visible only to its author, the shipper and staff. AT-213 an owner cannot nominate an asset it does not control. AT-214 a second open quotation from the same organisation is refused |

Fixed-price booking (a shipper sets a price and the first eligible party takes it) is a variant of this journey with the roles reversed. Whether it exists at launch is D-005.

## 6. Journey J4: negotiation and acceptance

| Aspect | Specification |
|---|---|
| Actors and permissions | Shipper `admin` or a `member` allowed to commit the organisation (permission **TBD** P-207); the quotation's author |
| Negotiation | Either side may counter: amount, validity, earliest pick-up. Each counter is a new version with its own validity; the previous version becomes unacceptable. Maximum rounds: **TBD** P-202 |
| Acceptance | The shipper accepts the latest version from the carrier, or the carrier accepts the shipper's latest counter. Acceptance names the exact version |
| Validation at the moment of acceptance | Checked again on the server, whatever the screen showed: shipment is `published` and on the quoted version; quotation version is the latest, open and not past its validity; both organisations still verified and eligible; nominated resources still eligible |
| Concurrent acceptance | The shipment row is locked for the acceptance. If two acceptances arrive together (two shipper users, or shipper and carrier each accepting different versions), the first to obtain the lock wins; the second finds the shipment `awarded` and is refused with "already awarded" |
| Acceptance racing withdrawal or expiry | Same lock. Whichever is saved first stands; an acceptance arriving after expiry is refused even if the screen still showed the quotation as open |
| Expired quotation | Cannot be accepted or revived. The shipper may ask the author to resubmit; a new quotation is a new record |
| Result | One transaction: quotation `accepted`, shipment `awarded`, booking created (section 7), reservations created, other quotations `not_selected`, messages queued |
| Failure paths | Lost race (told who is not disclosed, only that it is awarded); expired; stale version (reload); resource conflict (section 7) |
| Notifications | Counter received; accepted; not selected; refused acceptance with reason |
| Audit events | `quotation.countered` (with version), `quotation.accepted`, `quotation.not_selected`, `acceptance.refused` (with reason code) |
| Acceptance | AT-221 under simultaneous acceptance of two quotations, exactly one booking exists afterwards. AT-222 acceptance one second after validity end is refused. AT-223 accepting a superseded version is refused. AT-224 a retried acceptance with the same key returns the same booking and creates nothing new. AT-225 the accepted amount on the booking cannot be changed afterwards |

## 7. Journey J5: booking and resource reservation

| Aspect | Specification |
|---|---|
| Booking fields | Shipment version; accepted quotation version; both organisations; agreed amount and currency (immutable); snapshot of the commercial terms and policies in force at acceptance (cancellation, waiting time, payment terms: content **TBD**, structure fixed); pick-up and delivery windows; nominated truck, trailer, driver; who accepted and when |
| Reservation fields | Resource kind (truck, trailer, driver); resource; booking; period; state |
| Reservation period | From planned start to latest delivery plus a buffer. Whether travel to the pick-up point is included, and the buffer length, are **TBD** (P-206) |
| Integrity rule | The database refuses two `active` reservations for the same resource with overlapping periods. This is a database constraint, not an application check, and applies whichever organisation asks. Back-to-back periods are allowed (3.1) |
| What is checked besides overlap | Operating control (Part 1, 3.5); asset and trailer compatibility with the shipment; a trailer present where the truck is a tractor head or the shipment requires one; documents valid through the period; for a nominated driver: affiliation, authorisation and licence class (Part 1, 3.6). Dispatch authorisation is still required later (Part 3) |
| Driver not yet nominated | If P-201 allows it, the booking is confirmed with truck and trailer reserved and a "driver required by" deadline; the driver reservation is created when a driver is assigned and can still be refused for overlap |
| Reservation conflict at acceptance | The whole acceptance is rolled back; nothing is half-saved. The shipper is told only that this quotation cannot be accepted at present. **No replacement is promised.** The author is informed and may act under 7.2. Other quotations stay open |
| Substitution | Governed by the commercial rules in 7.2 |
| Notifications | Booking confirmed to both sides; resource conflict to the author; driver deadline approaching; substitution |
| Audit events | `booking.created`, `reservation.created`, `reservation.conflict_refused`, `reservation.released`, `booking.resource_substituted` |
| Acceptance | AT-231 with two simultaneous acceptances that need the same truck for overlapping periods, one booking is confirmed and the other acceptance leaves no booking and no reservation. AT-232 the same test for a trailer and for a driver shared by two organisations. AT-233 periods that touch but do not overlap both succeed. AT-234 for every lifecycle state in 7.3 the consistency check reports nothing for a correct booking and reports each seeded violation; a completed booking with consumed reservations is not reported. AT-235 a failed notification does not undo the booking and is retried. AT-236 a substitution either fully takes effect or leaves the original reservations untouched. AT-237 later changes to settings do not alter the terms snapshot of an existing booking |

### 7.1 Availability flag and concurrency protection

When a booking reserves a resource, other open quotations that nominate the same resource for an overlapping period can no longer be accepted as they stand. They are marked with an advisory **availability flag**; the binding check remains the one made at acceptance.

| Rule | Detail |
|---|---|
| Nature | A flag on a specific quotation **version**, not a state. It never changes the quotation's state, price, validity or content |
| How it is set | By a follow-up job after the booking is saved. For each candidate the job re-reads the quotation under a row lock and sets the flag **only if** the quotation is still open, is still on the version the job observed, still nominates that resource, and the overlap still exists. Otherwise it does nothing and logs the skip |
| What it can never do | Overwrite or revive a quotation that was withdrawn, expired, rejected, accepted or replaced by a newer version in the meantime |
| Clearing | A new version from the author clears the flag for that version. If the blocking reservation is released, the flag is cleared by the same compare-and-set rule |
| Delayed or repeated job | Safe: the job is idempotent and every write is conditional on current version and state |
| Acceptance | AT-238 a delayed conflict job leaves a withdrawn quotation withdrawn and does not touch a newer version. AT-239 the flag clears when the blocking reservation is released and the version is unchanged. AT-240 a flagged quotation whose conflict has gone can be accepted; an unflagged one whose resource is taken is still refused at acceptance |

### 7.2 Resource substitution: commercial rules

Substitution is a proposal with checks and, where required, the shipper's acceptance. It is never automatic. The consent rule itself depends on the approved contract terms (D-001) and is an **approved rule, not a setting**.

| Aspect | Before acceptance (quotation cannot be accepted as it stands) | After booking, before dispatch |
|---|---|---|
| Who proposes | The quotation's author only | The carrier or owner holding operating control; or operations within an intervention case (Part 1, 3.7) |
| Form | A new quotation version naming the substitute. It may keep or change the price; the shipper sees exactly what changed | A substitution proposal attached to the booking. **The price cannot change through substitution**; a price change is a booking amendment needing both parties |
| Hard requirements (system; nobody can waive them) | Substitute is under the proposer's operating control; verified; documents valid through the period; of an equipment and trailer type the shipment's stated requirement accepts; capacity and dimensions at least those the shipment requires; every special requirement met; a trailer where one is needed; driver licence class and authorisation where a driver is substituted; free for the period and not occupied by another trip | The same hard requirements. A substitute that fails any of them ends as `failed_checks` and **cannot be put to the shipper**; the shipper's consent cannot make it eligible |
| Classification of an eligible substitute | — | "Like-for-like": same equipment and trailer type as the one replaced. "Different": another type the shipment's requirement accepts, a smaller resource that still meets the stated requirement, or one that needs a changed pick-up time inside the agreed window |
| If the parties want something outside the requirement | The shipper issues a new shipment version; quotations are re-confirmed (section 4) | The shipment requirement itself must be changed by a booking amendment agreed by both parties. The checks are then run again against the amended requirement |
| Shipper acceptance | Ordinary acceptance of the new version; nothing is implied by the earlier one | "Different": always requires shipper acceptance. "Like-for-like" truck or trailer: **rule TBD (P-205)**; provisional position is that shipper acceptance is required unless the approved booking terms permit like-for-like substitution with notice. Driver change: notice to the shipper; consent rule also under P-205 |
| Holding the substitute | Not held; a quotation never reserves | Reserved from the moment of proposal as a "proposed substitute" reservation, so it cannot be booked elsewhere while the shipper decides; released if the proposal fails |
| Deadlines | The quotation's own validity. No substitute by then: the quotation expires | Proposal no later than a cut-off before the pick-up window; shipper response period. Both lengths are operating parameters (section 10) |
| States | Those of a quotation version | `proposed` → `accepted` / `declined` / `expired` / `withdrawn` / `failed_checks` |
| Failure outcomes | Quotation expires or is withdrawn; the shipper chooses among the remaining quotations or republishes | Declined, expired or failed: the original resources stay if they are still valid. If they are not (breakdown, suspension, expiry), the booking is marked **at risk** and an operations case opens; outcomes are a new proposal, or cancellation recorded against the party unable to perform. Nothing is cancelled automatically |
| Taking effect | — | One transaction: the substitute's reservation becomes the booking's reservation and the original is released |
| Audit events | `quotation.countered` | `substitution.proposed`, `substitution.checks_failed`, `substitution.accepted`, `substitution.declined`, `substitution.expired`, `booking.at_risk`, `booking.resource_substituted` |
| Acceptance tests | AT-245 a refused acceptance produces no substitute and no message promising one | AT-246 a "different" substitute cannot take effect without the shipper's recorded acceptance. AT-247 a substitution cannot alter the agreed amount. AT-248 a proposed substitute cannot be booked elsewhere while the proposal is open and is free again when it fails. AT-249 an expired proposal with invalid original resources opens an operations case and cancels nothing. AT-255 a substitute with insufficient capacity or a missing special requirement fails the checks and cannot be accepted by the shipper |

### 7.3 Reservations expected in each lifecycle state

The consistency check uses this table. "Trailer" applies only where the booking requires one.

| Booking and trip state | Truck | Trailer | Driver |
|---|---|---|---|
| Confirmed, driver not yet named (if P-201 allows) | 1 active | 1 active | none |
| Confirmed, all named | 1 active | 1 active | 1 active |
| Substitution proposed | 1 active, plus 1 active "proposed substitute" for the kind being replaced | same | same |
| Substitution taken effect | New one active; original `released` | same | same |
| Dispatched and in progress | 1 active | 1 active | 1 active |
| In progress beyond the reserved period (overrun) | 1 active, marked overrun; the period is extended where no later reservation blocks it | same | same |
| Under intervention hold | Unchanged until operations decides | same | same |
| Delivered and trip closed | 0 active; 1 `consumed` | 0 active; 1 `consumed` | 0 active; 1 `consumed` |
| Cancelled before dispatch | 0 active; all `released` | same | same |
| Cancelled after dispatch (Part 4) | Released when operations confirms the resource is free | same | same |

**Occupancy is separate from the reserved period.** A truck, trailer or driver is *occupied* from the moment its trip starts until the trip is delivered or operations confirms the resource is free. Occupancy does not end because the reserved period has ended.

| Rule | Detail |
|---|---|
| One trip at a time | The database allows at most one trip in progress per truck, per trailer and per driver. This holds under simultaneous requests and does not depend on reservation periods |
| Overrun | Recorded when a trip is still in progress past its reserved period. The period is extended where no later reservation blocks it; where one does, the database refuses the extension and the overrun is recorded against the resource |
| Effect on the next booking | It is marked **at risk**, its parties and operations are notified, and **its dispatch is blocked** while any of its resources is occupied: authorisation is refused and a trip start is refused (Part 3, section 3) |
| Ways forward | The resource becomes free; a substitution takes effect under 7.2; or operations records a cancellation. Nothing is automatic |
| Acceptance | AT-254 with a truck still on an overrunning trip, the next booking for that truck cannot be authorised or started although the first reservation period has ended; it can once the truck is free or substituted |

Violations reported by the check: a confirmed or in-progress booking missing an expected active reservation; an active reservation whose booking is cancelled or closed; a closed booking with no consumed truck reservation; a "proposed substitute" reservation with no open proposal. Released and consumed reservations on finished bookings are correct and are not reported.

## 8. Journey J5b: cancellation before dispatch and reservation release

Cancellation after dispatch, and all fees and refunds, belong to Part 4 and finance.

| Aspect | Specification |
|---|---|
| Before award | Shipper withdraws the shipment: all open quotations close; nothing was reserved; no fee question arises |
| After booking, by the shipper | Booking `cancelled`; reservations `released` in the same transaction; reason and time before pick-up recorded |
| After booking, by the carrier or owner | Same, plus the shipper chooses: republish (a new publication; old quotations are not revived) or close |
| By operations | Same effect, with a reason code and staff identity; used for verification failures, safety and fraud interventions (Part 1, 3.7) |
| Driver deadline missed | Booking flagged to operations and both parties; automatic cancellation or not is **TBD** (P-204) |
| Fees and refunds | Not calculated here. The cancellation record stores who cancelled, when, how long before the pick-up window, the reason and the booking's policy snapshot, so the approved policy (D-008) can be applied later without guessing |
| Release rule | A reservation is released only by cancellation, substitution or trip completion, always in the same transaction as the event that causes it. Early completion releases the remaining time |
| Validation | Only a `confirmed`, not-yet-dispatched booking can be cancelled here; a second cancellation request returns the first result |
| Notifications | Both parties, the assigned driver if any, operations where the pick-up is near (threshold **TBD**) |
| Audit events | `booking.cancelled` (actor, reason, lead time), `reservation.released`, `shipment.republished` |
| Acceptance | AT-241 after cancellation the same truck can be booked for the same period immediately. AT-242 a repeated cancellation request has one effect. AT-243 cancellation and a simultaneous substitution cannot leave an active reservation on a cancelled booking. AT-244 the cancellation record contains every fact needed to apply a fee policy later |

## 9. Where the three open decisions change this part

The comparisons below are **illustrative only**. Payment deadlines, price visibility, liability, invoicing and tax treatment must follow the approved contracts and professional legal and accounting review.

**D-001 Commercial model: workflow differences (not built)**

Holds under either model and can be relied on now: shipment drafting and publication (section 4), time rules (3.1), retry rules (3.2), failure recovery (3.3), database-enforced reservations (7, 7.3), the concurrency protections (6, 7.1).

Depends on D-001 and must be redrawn if principal is chosen: who authors and who accepts an offer, the parties to a booking and whether there is one agreement or two linked ones, which prices exist and who sees them, whose consent a substitution needs, who cancels against whom, and which documents are issued.


| Point in the flow | If agent | If principal | Provisional draft in this document (agent-shaped) |
|---|---|---|---|
| Whose offer the shipper accepts | The carrier's or owner's | Trucker's | Quotation is authored by the carrier or owner |
| Prices held | One transport price; platform fee separate | Two prices: what the shipper pays and what the carrier receives | Quotation stores the carrier's amount only; no fee or margin field is built |
| What each side sees | Typically the same transport price | Typically only its own price | Follows from the contracting structure; decided with D-001, not a setting |
| Carrier identity before acceptance | Usually visible | May be withheld | **TBD**, decided with D-001 |
| Booking parties | Shipper and carrier, platform as intermediary | Two linked agreements with Trucker in the middle | Booking records shipper and carrier organisations and a terms snapshot |
| Who may cancel against whom | Shipper and carrier against each other | Each against Trucker | Cancellation record stores facts only |
| Documents issued at booking | Confirmation between shipper and carrier | Order confirmation to the shipper, transport order to the carrier | Not designed until decided |

**D-002 Payment approach**

| Point | Effect |
|---|---|
| Between acceptance and confirmation | A prepayment or deposit approach would add a `pending_payment` step and a time limit during which resources are held. Not designed |
| Reservation timing | If payment must precede confirmation, the hold-while-paying period and its expiry become a policy |
| Booking snapshot | Carries the payment terms once they exist |

**D-003 Launch geography**

| Point | Effect |
|---|---|
| Currency | One currency, or currency chosen per shipment by country; amounts already carry currency |
| Shipment fields | Cross-border lanes add border crossing, customs documents and who handles clearance |

| Time | Different zones at pick-up and delivery (handled in 3.1) |
| Enabled lanes | Carry-over C-02 and C-03 |
